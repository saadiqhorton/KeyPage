# Release controls and operator checklist

This runbook defines the repository controls and evidence required for a KeyPage
release. It does not authorize a release, deployment, merge, tag change, or
ruleset change.

## Main-branch ruleset

The reviewed API payload is [`.github/rulesets/main.json`](../.github/rulesets/main.json).
It applies only to the default branch and enforces:

- pull requests with one approval and all conversations resolved;
- dismissal of stale approvals after new commits;
- a current branch before merge (`strict_required_status_checks_policy`);
- no branch deletion or non-fast-forward updates; and
- the four required GitHub Actions contexts below.

| Required context | Workflow | Job |
| --- | --- | --- |
| `typecheck · test · build` | CI | `check` |
| `docker compose smoke` | CI | `docker-smoke` |
| `disposable snapshot rollback` | Rollback drill | `snapshot-rollback` |
| `sonarqube` | SonarQube | `sonarqube` |

These exact contexts were observed on successful pull-request commit
`470e10ca586b437892249262f2b575378d76c1b7`. External review bots are not
required because their availability and conclusions are not controlled by this
repository.

The sole recovery bypass is GitHub repository role ID `5` (Repository Admin).
It exists for owner recovery from a broken ruleset. Do not use it for normal
merges or releases. If recovery is unavoidable, record the reason, affected
commit, actor, and restoration verification in the pull request or incident.

### Apply or update the ruleset

Only a repository owner may perform this step, after the pull request containing
the workflow and payload has merged and all four check names have been observed
again on that pull request.

1. Confirm there is no overlapping branch protection or ruleset with conflicting
   required checks.
2. Confirm the JSON is valid: `jq empty .github/rulesets/main.json`.
3. Create the ruleset without altering the payload:

   ```bash
   gh api --method POST repos/saadiqhorton/KeyPage/rulesets \
     --input .github/rulesets/main.json
   ```

4. Open a test pull request. Verify all four required checks are created and the
   merge gate clears only after they pass, one non-stale approval exists, and all
   review threads are resolved.
5. Verify a direct update and force-push to `main` are rejected. Do not use the
   admin bypass for this test.
6. Record the ruleset ID, API response, test pull request, and check-run URLs.

If a required context is renamed or stops being created, the repository admin
can use the explicit recovery bypass to repair or disable this one ruleset.
Restore active enforcement immediately after the repair and record the event.

## Release artifact workflow

`.github/workflows/release-artifacts.yml` runs for `v[0-9]*` tag pushes and by
manual dispatch for a dry run. It has read-only repository access plus only the
OIDC and attestation permissions needed for GitHub artifact provenance. It does
not create a GitHub Release, push a tag, publish a package, or deploy.

The workflow rejects a pushed release tag whose commit is not an ancestor of
`origin/main`. It emits one workflow artifact containing:

- `keypage-<ref>-<commit>.tar.gz`: deterministic `git archive` source bundle;
- the matching `.spdx.json`: SPDX 2.3 SBOM generated by pinned Syft;
- `SHA256SUMS`: immutable SHA-256 digests for the bundle and SBOM; and
- GitHub provenance attestations for all three files and an SBOM attestation
  binding the SPDX document to the source bundle.

Third-party actions and the Syft binary are pinned to immutable versions. Update
them only in a reviewed dependency change that records the upstream release and
resolved commit SHA.

## Release checklist

### Candidate preparation

- [ ] Choose a new SemVer tag. Do not reuse or move an existing tag.
- [ ] Confirm the candidate commit is on `main` and identify its full SHA.
- [ ] Confirm the ruleset is active and the candidate pull request passed all
      four required contexts with a current approval.
- [ ] Review user-visible, security, configuration, data migration, backup, and
      rollback changes since the previous release.
- [ ] Run a manual `Release artifacts` dry run for the exact candidate SHA.
- [ ] Download the workflow artifact and verify it locally:

  ```bash
  cd <downloaded-artifact-directory>
  sha256sum --check SHA256SUMS
  jq -e '.spdxVersion == "SPDX-2.3" and (.packages | length > 0)' \
    keypage-*.spdx.json
  gh attestation verify keypage-*.tar.gz --repo saadiqhorton/KeyPage
  gh attestation verify keypage-*.tar.gz --repo saadiqhorton/KeyPage \
    --predicate-type https://spdx.dev/Document
  gh attestation verify keypage-*.spdx.json --repo saadiqhorton/KeyPage
  gh attestation verify SHA256SUMS --repo saadiqhorton/KeyPage
  ```

- [ ] Extract the source bundle in a disposable directory, build it, run the
      health check on port `9090`, and complete the rollback drill.

### Authorized release

- [ ] Obtain the repository owner's approval to create the new tag and publish
      the release. Approval of this document alone is not release authorization.
- [ ] Create the annotated tag at the already-reviewed candidate SHA and push it
      without force. Never retag an existing version.
- [ ] Wait for `package · SBOM · provenance` to pass for the tag.
- [ ] Verify the tag workflow's files, checksums, SBOM, and attestations again.
- [ ] Draft release notes with the full commit SHA, artifact SHA-256 values,
      upgrade steps, rollback notes, known risks, and breaking changes.
- [ ] Attach the exact verified files to the GitHub Release. Do not rebuild them.
- [ ] Publish only after an owner compares the attachments to `SHA256SUMS`.

### Recovery and evidence

- [ ] Preserve the release URL, tag object SHA, commit SHA, workflow run URL,
      artifact names and digests, attestation verification output, SBOM
      validation output, and approver identity.
- [ ] If verification fails, stop. Do not publish, replace files, move the tag,
      or deploy. Correct the cause through a new pull request and use a new
      version tag after review.
- [ ] If an operator deployment fails, use [`docs/rollback.md`](rollback.md) and
      record the last-known-good commit, snapshot, health evidence, and owner.
